# 🧪 Лабораторная работа: «Создание Knowledge Graph в Microsoft Fabric IQ»

**Длительность:** 120 минут  
  
**Сценарий:** Сеть больниц Lamna Healthcare — нужно связать больницы, отделения, палаты, пациентов и оборудование мониторинга, чтобы отвечать на вопросы вида «какое оборудование отслеживает каких пациентов и в каких отделениях».

---

## 🗺️ Общая карта лабораторной (120 минут)

| Этап | Что делаем | Время |
|---|---|---|
| **0** | Подготовка среды: workspace, Lakehouse, загрузка данных | 15 мин |
| **1** | Создание пустой **Ontology** | 5 мин |
| **2** | Определение **Entity Types** | 15 мин |
| **3** | Создание **Properties** и **Keys** | 15 мин |
| **4** | Определение **Relationships** | 15 мин |
| **5** | **Data binding** к OneLake (Lakehouse + Eventhouse) | 20 мин |
| **6** | **Построение графа** (материализация) | 10 мин |
| **7** | **Визуальное исследование** взаимосвязей | 20 мин |
| **8** | Рефлексия и критерии оценки | 5 мин |

## Этап 0. Подготовка среды (15 минут)

### 0.1. Создайте workspace

1. Перейдите на `https://app.fabric.microsoft.com` и войдите с учётными данными Fabric.
2. На левой панели выберите **Workspaces** → **New workspace**.
3. Задайте имя (например, `Lamna_Healthcare_Lab`) и выберите лицензионный режим **Fabric Trial** или **Power BI Premium**.

### 0.2. Создайте Lakehouse и загрузите статические данные

1. В workspace выберите **+ New item → Lakehouse**.
2. Назовите Lakehouse `LamnaHealthcareLH` и нажмите **Create**.
3. Скачайте архив с sample-данными: `sample-data.zip`.
4. Распакуйте. В архиве — **пять CSV-файлов**:
   - `Hospitals.csv` — больницы;
   - `Departments.csv` — отделения (ICU, Emergency, Surgical);
   - `Rooms.csv` — палаты внутри отделений;
   - `Patients.csv` — текущие пациенты и их палаты;
   - `VitalSignEquipment.csv` — оборудование, назначенное пациентам.
5. В Lakehouse нажмите **Upload files** и загрузите **пять** CSV-файлов (все, кроме `VitalSignsReadings.csv` — он пойдёт в Eventhouse).
6. После загрузки **преобразуйте каждый CSV в таблицу** (щелчок правой кнопкой → **Load to table** или **Convert to table**). Убедитесь, что в разделе **Tables** появились пять таблиц: `Hospitals`, `Departments`, `Rooms`, `Patients`, `VitalSignEquipment`.

### 0.3. Создайте Eventhouse для потоковых данных (телеметрия)

1. В том же workspace выберите **+ New item → Eventhouse**.
2. Назовите его `LamnaVitalsEH` и создайте KQL database внутри.
3. Загрузите `VitalSignsReadings.csv` в таблицу (например, через **Get data → Local file**). Это данные временных рядов: показания сердечного ритма и кислорода, собранные с мониторов.

> 💡 **Зачем два источника?** Lakehouse даёт **статические** данные (больницы, палаты, пациенты). Eventhouse даёт **временные ряды (time series)** — показания оборудования. Ontology умеет привязываться к обоим, но **Eventhouse поддерживает только `TimeSeries`-привязку**, а статика должна приходить из Lakehouse.

## Этап 1. Создание пустой Ontology (5 минут)

1. В workspace выберите **+ New item**.
2. Найдите **Ontology (preview)** и выберите его.
3. Задайте имя `LamnaHealthcareOntology`. Имя может содержать буквы, цифры и подчёркивания — **без пробелов и дефисов**.
4. Нажмите **Create**. Откроется пустая онтология с **Home configuration canvas**.

> 📌 **Что такое Ontology?** Это семантический слой, который определяет бизнес-сущности, их свойства и отношения, а затем привязывает их к реальным данным. Ontology **не копирует данные** — она создаёт описание поверх OneLake.

## Этап 2. Определение Entity Types (15 минут)

**Entity Type** — это тип бизнес-объекта. В нашем сценарии их **шесть**: `Hospital`, `Department`, `Room`, `Patient`, `VitalSignEquipment`, `VitalSignsReading`.

### 2.1. Создайте Entity Type «Hospital»

1. На холсте конфигурации нажмите **+ Add entity type** (или **New entity type**).
2. Введите имя: `Hospital`.
3. **Пока не привязывайте данные** — сначала создадим все типы «на бумаге», затем добавим свойства и ключи.

### 2.2. Создайте остальные пять Entity Types

Повторите шаг 2.1 для:
- `Department`
- `Room`
- `Patient`
- `VitalSignEquipment`
- `VitalSignsReading`

> 💡 **Совет по именованию:** используйте **бизнес-термины** в единственном числе и PascalCase. Это станет основой бизнес-словаря: потребители онтологии (аналитики, AI-агенты) будут видеть `Patient`, а не `dim_patients`.

---

## Этап 3. Создание Properties и Keys (15 минут)

**Property** — атрибут сущности. **Key** — уникальный идентификатор экземпляра Entity Type. Только **строковые (`string`)** и **целочисленные (`integer`)** свойства могут быть ключами.

### 3.1. Добавьте свойства для `Hospital`

1. Откройте Entity Type `Hospital`.
2. На вкладке **Properties** нажмите **Add property**.
3. Создайте:
   - `HospitalId` — тип **string** (это будет ключ);
   - `HospitalName` — string;
   - `City` — string;
   - `BedCount` — integer.

### 3.2. Назначьте ключ

1. В списке свойств `Hospital` найдите `HospitalId`.
2. Откройте его контекстное меню и выберите **Set as key** (или **Use as key**).
3. Убедитесь, что ключ отмечен значком 🔑.

> ⚠️ **Правило:** ключ должен быть **уникальным** для каждого экземпляра. Если в данных есть дубликаты `HospitalId`, привязка данных завершится ошибкой.

### 3.3. Добавьте свойства для остальных типов (аналогично)

| Entity Type | Свойства (минимум) | Ключ |
|---|---|---|
| `Department` | `DepartmentId` (string), `DepartmentName` (string), `DepartmentType` (string) | `DepartmentId` |
| `Room` | `RoomId` (string), `RoomNumber` (string), `RoomType` (string) | `RoomId` |
| `Patient` | `PatientId` (string), `PatientName` (string), `AdmissionDate` (datetime — **не ключ**) | `PatientId` |
| `VitalSignEquipment` | `EquipmentId` (string), `EquipmentType` (string), `MonitoringStart` (datetime — **не ключ**) | `EquipmentId` |
| `VitalSignsReading` | `ReadingId` (string), `HeartRate` (integer), `OxygenLevel` (integer), `ReadingTimestamp` (datetime — **не ключ**) | `ReadingId` |

> 📌 **Почему даты не могут быть ключами?** Fabric Ontology разрешает в качестве ключей только строковые и целочисленные свойства. Даты и вещественные числа могут быть **свойствами**, но не ключами.

---

## Этап 4. Определение Relationships (15 минут)

**Relationship Type** — это именованная связь между двумя Entity Types. В нашем сценарии — **пять** связей.

### 4.1. Создайте Relationship Type «contains» (Hospital → Department)

1. На холсте онтологии нажмите **+ Add relationship** (или **New relationship type**).
2. **Имя:** `contains` (строчными буквами, в бизнес-терминах).
3. **Origin entity type:** `Hospital`.
4. **Target entity type:** `Department`.

### 4.2. Создайте остальные связи

| Имя связи | Origin | Target | Бизнес-смысл |
|---|---|---|---|
| `contains` | `Hospital` | `Department` | Больница содержит отделения |
| `contains` | `Department` | `Room` | Отделение содержит палаты |
| `assignedTo` | `Patient` | `Room` | Пациент назначен в палату |
| `monitors` | `VitalSignEquipment` | `Patient` | Оборудование мониторит пациента |
| `produces` | `VitalSignEquipment` | `VitalSignsReading` | Оборудование генерирует показания |

> 💡 **Направление имеет значение:** `monitors` направлено **от оборудования к пациенту**. Это семантика: «оборудование мониторит пациента», а не наоборот. Правильное направление упрощает написание GQL-запросов в дальнейшем.

### 4.3. Проверьте графовую схему

На холсте конфигурации вы должны увидеть **шесть узлов** (Entity Types) и **пять рёбер** (Relationship Types). Это ваша **графовая схема** — она определяет, какие связи вообще возможны в Knowledge Graph.

> ⚠️ **Связи без данных не визуализируются:** Relationship Type можно определить «абстрактно», но пока данные не привязаны, в представлении Entity Type Details связь не будет отображаться. Поэтому переходим к binding.

## Этап 5. Data Binding к OneLake (20 минут)

**Data Binding** соединяет схему онтологии с конкретными таблицами в OneLake. Данные **не копируются** — онтология ссылается на источник.

### 5.1. Привязка статических данных из Lakehouse

Начните с `Hospital`.

1. На холсте конфигурации нажмите **…** рядом с `Hospital` → **Bind data**.
2. Нажмите **+ (plus)** рядом с **Data sources** → выберите **OneLake**.
3. В каталоге OneLake выберите ваш workspace → `LamnaHealthcareLH` → таблицу **`Hospitals`**.
4. Fabric предложит **автоматическое сопоставление** колонок таблицы со свойствами Entity Type:
   - `HospitalId` → `HospitalId` (ключ);
   - `HospitalName` → `HospitalName`;
   - `City` → `City`;
   - `BedCount` → `BedCount`.
5. Проверьте типы и нажмите **Save** (или **Bind**).

> 💡 **Что произошло?** Ontology «узнала», что каждый экземпляр `Hospital` — это строка в таблице `Hospitals`. Колонка `HospitalId` стала ключом, а остальные — свойствами.

### 5.2. Привяжите остальные статические сущности (повторите для каждой)

| Entity Type | Таблица в Lakehouse | Ключевая колонка |
|---|---|---|
| `Department` | `Departments` | `DepartmentId` |
| `Room` | `Rooms` | `RoomId` |
| `Patient` | `Patients` | `PatientId` |
| `VitalSignEquipment` | `VitalSignEquipment` | `EquipmentId` |

### 5.3. Привязка временных рядов из Eventhouse

1. Откройте `VitalSignsReading`.
2. Нажмите **Bind data** → **+ Data sources** → **OneLake** → **`LamnaVitalsEH`** (Eventhouse).
3. Выберите таблицу с показаниями (например, `VitalSignsReadings`).
4. **Важно:** для Eventhouse доступна только **TimeSeries**-привязка. Убедитесь, что свойства `HeartRate`, `OxygenLevel` и `ReadingTimestamp` привязаны **как временные ряды**.
5. Нажмите **Save**.

> ⚠️ **Статика и временные ряды:** если свойство должно быть статическим (например, `EquipmentType`), его нельзя привязать к Eventhouse — только к Lakehouse. Eventhouse предназначен **исключительно для time series**.

### 5.4. Привязка связей (Relationships) к данным

Связи тоже нужно «наполнить» данными. Для каждой Relationship Type укажите, **из какой таблицы** брать информацию о связи.

1. Откройте Relationship Type `contains` (Hospital → Department).
2. Нажмите **Bind data**.
3. Укажите таблицу, где хранится связь: `Departments` (в ней есть внешний ключ `HospitalId`).
4. Сопоставьте **ключ origin** (`Hospital.HospitalId`) и **ключ target** (`Department.DepartmentId`) с соответствующими колонками в таблице.
5. Повторите для всех пяти связей.

> 💡 **Совет:** если связь «многие-ко-многим» хранится в отдельной таблице (например, `VitalSignEquipment` содержит и `EquipmentId`, и `PatientId`), укажите эту таблицу как источник связи.

## Этап 6. Построение графа (материализация) (10 минут)

После привязки данных онтология **знает**, где лежат данные. Теперь нужно **материализовать граф** — создать исполняемую графовую структуру для обхода и визуализации.

### 6.1. Откройте Manage graph

1. В онтологии на ленте найдите **Manage graph** (или **Graph** → **Manage**).
2. Выберите **подмножество** сущностей для материализации. Для лабораторной материализуйте **все шесть Entity Types** и **все пять Relationship Types**.

> 💡 **Можно материализовать не всё:** если онтология большая, выбирайте только те сущности и связи, которые нужны для конкретных бизнес-вопросов. Это ускорит материализацию.

### 6.2. Запустите материализацию

1. Нажмите **Materialize** (или **Build graph**).
2. Дождитесь завершения. Время зависит от объёма данных — от **нескольких минут** до часов. Для sample-данных это обычно **1–3 минуты**.
3. После завершения граф станет **queryable** — оптимизированным для обхода (traversal) и сопоставления паттернов.

> ⚠️ **Не меняйте схему после материализации без перезагрузки:** Graph в Fabric **не применяет структурные изменения инкрементально**. Если вы добавите свойство или измените тип узла/ребра, потребуется **полная перезагрузка** данных (Save → reload).

## Этап 7. Визуальное исследование взаимосвязей (20 минут)

### 7.1. Откройте визуализацию графа

1. В онтологии на ленте нажмите **Explore graph** (или откройте материализованный Graph item напрямую).
2. Откроется **Query Builder** — визуальный интерфейс для исследования графа.

### 7.2. Выполните базовый обход (traversal)

1. В Query Builder выберите стартовый узел: например, `Hospital` с именем «Lamna General Hospital».
2. **Разверните узел** (Expand): вы увидите связанные с ним `Department` (через ребро `contains`).
3. Разверните один из `Department` — появятся связанные `Room`.
4. Разверните `Room` — появятся `Patient`, назначенные в эту палату.
5. Разверните `Patient` — появятся `VitalSignEquipment`, которые его мониторят.

> 💡 **Что вы только что сделали?** Выполнили **multi-hop traversal** — обход на несколько шагов от больницы к оборудованию. В реляционной БД для этого потребовалось бы **четыре JOIN’а**; в графе — четыре визуальных «разворота».

### 7.3. Найдите ответ на бизнес-вопрос

**Вопрос:** «Какое оборудование мониторит пациентов в отделении ICU больницы Lamna General?»

1. Начните с `Hospital` (Lamna General).
2. Разверните `Department` → выберите `ICU`.
3. Разверните `Room` → разверните `Patient`.
4. Разверните `VitalSignEquipment` у каждого пациента.
5. **Результат:** вы видите цепочку «Больница → Отделение → Палата → Пациент → Оборудование».

### 7.4. Исследуйте свойства узлов

1. Наведите курсор на узел `VitalSignEquipment`.
2. Откроется панель **Properties** с `EquipmentType`, `MonitoringStart` и другими атрибутами.
3. Убедитесь, что данные из Lakehouse (статика) и Eventhouse (time series) корректно отображаются.

### 7.5. (Опционально) Выполните GQL-запрос

Если вы хотите увидеть, как тот же обход выражается в коде, откройте **Code Editor** и выполните запрос вида:

```gql
MATCH (h:Hospital {HospitalName: 'Lamna General Hospital'})
      -[:contains]->(d:Department {DepartmentName: 'ICU'})
      -[:contains]->(r:Room)
      <-[:assignedTo]-(p:Patient)
      <-[:monitors]-(e:VitalSignEquipment)
RETURN h.HospitalName, d.DepartmentName, p.PatientName, e.EquipmentType
```

> 💡 **Синтаксис GQL** может отличаться в preview-версии. Главное — показать слушателям, что визуальный обход и GQL-запрос **эквивалентны**: это два способа выразить один и тот же графовый паттерн.
